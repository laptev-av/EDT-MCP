# Внедрение OpenSpec (spec-driven workflow) в репозиторий

Issue: [#130](https://github.com/DitriXNew/EDT-MCP/issues/130)

## Суть

Перевести разработку EDT-MCP на spec-driven подход через OpenSpec (`opsx`): каждое заметное изменение оформляется как change-предложение со спецификацией (дельтой), которое ревьюится **до** написания кода, а после реализации — верифицируется и архивируется.

## Контекст репозитория

- **EDT MCP Server** — Eclipse/Java-плагин для 1С:EDT (~214 `.java`), отдающий AI-ассистентам (Claude, Copilot, Cursor) набор MCP-инструментов.
- Разработка строго через PR: коммиты ссылаются на номера (`feat: ... (#119)`, `closes #112`), ~10 контрибьюторов, среди них `Copilot`, много feature/fix-веток.
- Каждый PR фактически добавляет **новый инструмент с контрактом** (`create_metadata_object`, `get_form_layout_snapshot`, `terminate_launch` и т.д.).
- Большой пласт документации: `docs_api-edt/`, `checks/`, двуязычные `rules/en` + `rules/ru`, `CLAUDE.md.example` (~199 `.md`).
- `openspec` CLI уже установлен глобально, скиллы OpenSpec в окружении доступны; каталога `openspec/` в репе пока нет.

## Зачем это нужно

- **Dogfooding (главное):** продукт делается *для* AI-агентов — логично и сам процесс вести через spec-driven AI-workflow. Это проверка собственного подхода в бою и устранение разрыва «делаем инструменты для агентов, но сами агентами процесс не ведём».
- **MCP-инструмент по природе = спецификация:** имя, параметры, формат ответа, группа, дефолты. Сейчас контракт живёт в коде + описательных `.md`, которые дрейфуют от реализации. OpenSpec фиксирует цепочку *намерение → spec → реализация → архив* и убирает дрейф `docs_api-edt/`.
- **Ритм «один инструмент за PR» идеально ложится на change-модель:** единица OpenSpec-change = одна фича/инструмент; дельта спеки ревьюится до кода, что для кросс-модульных правок (BSL + формы + каскадный рефакторинг метаданных) ловит проблемы дизайна заранее.
- **Много контрибьюторов и агенты в ревью:** структурированные предложения снижают неоднозначность одинаково для людей и для AI, улучшают онбординг, делают ревью предметным (обсуждаем согласованную спеку, а не дифф).
- **Уже есть задел «правил для ИИ», но описательный:** `rules/`, `CLAUDE.md.example`, `docs_api-edt` — это зачатки спеки без жизненного цикла. OpenSpec даёт им статус источника истины с верификацией и архивированием.

## Риски и издержки

- **Оверхед на мелочах:** для тривиальных багфиксов отдельный артефакт избыточен — их можно вести как раньше.
- **Нужна дисциплина:** спека без `verify`/`archive` протухнет так же, как сейчас `.md`.
- **Двуязычность:** поддержание специй в `en`/`ru` добавит работы, если решено тащить оба языка.
- **Стоимость входа близка к нулю:** CLI и скиллы уже стоят; внедрение инкрементальное — только для новых изменений, историю не переписываем, откат возможен в любой момент.

## Итог

OpenSpec закрывает разрыв между намерением, документацией и кодом в проекте, который сам по себе ориентирован на AI-агентов. Внедрение дешёвое и обратимое, ритм разработки (один инструмент за PR) уже совпадает с change-моделью, а пилот на одной фиче позволяет принять решение о масштабировании по факту, а не на словах.
